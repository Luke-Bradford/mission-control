# Overview content inventory and redesign proposal

Status: design draft for the requested content review; product implementation remains paused. Base is `606fb0b4` (including delivered shell PR #1370). Stopped PR #1374 is pushed at `2cab26c2`; its later local priority patch and gallery remain preserved, unpushed and unapproved. This design branch does not change product source.

The operator's latest steering is that Overview must stay high-level, retain key content including token capacity, add graph detail, and reduce excessive box padding. “We don't have to drop content, just make it fit better, which needs a redesign.” Seats and live activity remain primary; Pipeline is secondary. This supersedes continuing the density implementation.

## What changed, and what was actually hidden

The baseline and approved Overview mockup put Crew directly after stats, with Timeline beside it. PR #1374 moved Pipeline ahead of Crew, added a healthy headline, split narrower stats into two rows, and stacked Machine under Timeline. Those author choices increased the distance to Crew and live activity. The Pipeline promotion and tall primary sidebar were not requested by the approved mockup. No configured-row/state filter or Loops removal was introduced, but presence below the fold was treated too loosely as sufficient.

The KPI trace also lost visible detail: `KpiStrip.tsx` removed its −30m / now axis and changed its visible peak label to `sr-only`. The smaller side-by-side spark retained peak/latest only in SVG accessible text. That is a real removal of readable graph detail, not only movement. The redesign restores visible axes, units and peak/latest; every existing measured KPI series remains inspectable, while absent series stay explicitly uncollected.

Capacity has three separate meanings. **Context capacity** is `digest.contextTokens` used against `CrewRow.contextWindow`, with remaining derived only when both are known. **Provider allowance** is `/api/limits` percentage used in a 5h/7d window, with reset/forecast/freshness; it exposes no raw token allotment. **Machine seat capacity** is configured seats / maximum seats, session maximum, free memory and admission warning. Token rate is throughput, not any of these capacities.

Baseline and `2cab26c2` both show context only as a percent/bar, not numeric used/window/remaining. PR #1374 narrowed the Context track to 46px at 1280 expanded. Thus numeric capacity was not removed by this PR, but its percent-only presentation remained too weak and became crowded. The synthetic eleven-seat evidence used unknown context while the read-only live `/api/crew?shape=summary` response on 2 November supplied used/window values for all eleven rows. That fixture missed an important real shape; future evidence must include known and unknown capacity.

Actual read-only API audit: eleven rows comprise nine configured crew seats and two observed loops; all nine configured seats are present, including idle seats. FLIGHT is one of the nine. `All sessions` projects FLIGHT + eight other seat rows and two loop chips. Selecting the crew session excludes the two other-repo loops under the unchanged repo-following rule. This audit records shapes/counts only; the mockup uses fictional identities and values.

## Concrete layout proposal

1. Existing shell and session/FLIGHT controls; no healthy-state page hero.
2. Compact stats strip. At adequate content width, an independent primary column holds the 1050–1200px roster, Loops, live activity and full allowance table. The independent right column holds a compact provider/GitHub remaining/reset summary, measured Timeline/next actions, detailed token history and Machine. No tall shared row delays the live log.
3. At 1600 with FLIGHT open, full-width roster/Loops are followed by independent Activity/Timeline and allowance/throughput/Machine columns. The normal first screenful contains all eleven seats, several events, provider remaining/reset and the detailed throughput plot. At short height, fewer seat rows are visible; an actual-overflow cue names the retained count and visible count.
4. All measured KPI histories remain inspectable through the named history selector. Machine RAM chart is explicitly percentage, with used/total GiB alongside; disk is free GiB with a labelled axis. Missing samples remain gaps, unknown capacity remains unknown.
5. Compact secondary Pipeline lane summary. Existing evidence detail and test-lock controls remain reachable.

The draft proposes 8px vertical /12px horizontal panel interiors for repeated summaries, using existing spacing tokens, rather than today's16px around each interior. This responds to the requested padding redesign using existing spacing tokens; it is documented for content review, not applied as a global product token change. Type remains13/20 body,12/16 secondary,11px mono labels only; row32 compact /40 wide, controls24 minimum. At short heights roster scrolling makes live activity discoverable; all eleven seats are still retained. At the narrowest open rail, wide comparison data may use a named keyboard scroll region; actions/identifiers must stay visible and full values must be reachable. The rendered draft will determine whether that tradeoff is acceptable.

The standalone HTML has labelled fictional values mapped to actual fields. It is not a full-App implementation, a live reading or a final design pass. Render evidence must name that scope. No product code, provider/crew action, observed-loop change, live restart or new collection is part of this design branch.
