# Code-health plan for operator approval

Stage 2 of #1185, following the [research report](2026-11-01-code-health.md). This is a proposal: no mockup or build tickets have started. Approval of this plan permits the mockup stage only; the mockup needs separate approval before build tickets.

## The page's question

**Where should we invest in code health next, and what evidence supports that choice?**

Audit opens on recommendations for the selected repo, separate from its planned-work board. A repo selector and a shared 7/30/90-day window apply to every panel; 30 days is the default. A visible coverage line gives actual observed dates, analysed commit and collection age. Missing collection is distinct from zero findings. Cross-repo comparisons use small multiples with common scales, never one blended score.

The proposed tabs are **Overview**, **Review quality**, **Code risk** and **Test health**. Existing PR readiness remains in QA; Audit links there when acceptance work is the next action. Each tab fits at 1600×1000 without a page-length list. At 1280 or a 700-pixel-high window, sections may stack and scroll visibly; no panel clips content. Detail opens in a named drawer, preserving repo, range, filters and keyboard focus. All existing design-system minimum type and control sizes apply.

Bars start at zero; time charts use explicit axes, direct labels and at most four series. These choices follow the [Government Analysis Function chart guidance](https://analysisfunction.civilservice.gov.uk/policy-store/data-visualisation-charts/): aligned bars support category comparison, while limited series and common-scale small multiples make trends readable. Counts, percentages and percentage-point changes are labelled separately. Uncollected periods are gaps, never zero-valued points. A text table accompanies each chart; colour is never the only encoding. These are our proposed applications of the guidance.

## Recommendations and agent access

A recommendation is a durable record with repo, stable rule/version, evidence fingerprint, observation, uncertainty, proposal, target metric/direction, coverage and dates. Regenerating the same evidence updates the record rather than opening duplicates. The initial rules are deliberately conservative:

- **Recurring correction:** at least three distinct reported findings in the same category/file across at least two PRs within 30 days → inspect the shared cause and propose a narrow invariant or test. Uncategorised findings do not acquire an invented category.
- **Repeated review rounds:** a PR reaches three reported rounds → inspect its finding history and planning scope before extending the same work. This is a review-process observation, not a production defect claim.
- **Large and repeatedly changed file:** size is at least 1,000 lines and at least five distinct merged PRs touch it in 30 days → investigate a possible domain split. Show findings and growth when measured; the action remains an investigation until a coherent boundary is demonstrated.
- **Mixed CI outcome:** failure followed by success on the same commit/job identity → reproduce and classify. A named-test flaky recommendation requires per-test evidence; a job-only candidate never quarantines a test.

These thresholds are proposed triage defaults, not empirically validated defect predictors. Each rule displays why it fired and its coverage; thresholds become named constants with fixture tests. Sparse data produces a collection recommendation rather than a negative judgement about a repo.

Actions retain #989's intended lifecycle: **Accept**, **Dismiss with reason**, **Snooze until date**. Accept records an owner and creates a ticket through FLIGHT's existing authorised ticket path, or proposes a config change through its existing approval path. It never silently applies code or rules. Accepted work is linked to a deadline and a later comparison of the named metric. Marking **paid off** needs an explicit assessment against that baseline; correlation alone is not presented as causation. **No effect** retains evidence and a reason.

A proposed read-only `mc code_health` tool returns the same definitions, coverage, recommendations and bounded evidence refs as the UI. FAO's brief receives at most three relevant file recommendations, scoped to the ticket's declared/touched paths; broader seat area globs do not prove ticket scope. FLIGHT can inspect full evidence before acting. The web and agents share the server calculation, not separate scoring systems.
